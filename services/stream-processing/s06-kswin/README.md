
# S06: KSWIN Change Detection on Numeric Features

**Owner:** Asmar  
**Pipeline:** P5 (drift vs. attack)  
**Status:** Implemented and integration-tested

**Reference paper:** C. Raab, M. Heusinger, F.-M. Schleif, *Reactive Soft Prototype Computing for Concept Drift Streams*, Neurocomputing 416, 2020.

## 1. Purpose

S06 uses the Kolmogorov-Smirnov Windowing (KSWIN) method to detect changes in the statistical distribution of numeric features generated by agents.

It monitors three features:

- `argument_length`: length of the serialized tool-call arguments.
- `failure_rate`: binary failure observation (1.0 for failure, 0.0 for success).
- `anomaly_score`: numeric anomaly score produced by an upstream detector.

A detected distribution change produces a `drift.detected` event.

## 2. Architecture

```text
Kafka input topics
    |
    +-- tool-calls.A
    |
    +-- tool-calls.B
    |
    +-- scores
          |
          v
     S06 KSWIN
          |
          v
    Kafka topic: drift
          |
          v
    drift.detected
```

Each agent and monitored feature has its own independent detector.

## 3. Kafka topics

| Topic | Direction | Purpose |
|---|---|---|
| `tool-calls.A` | Input | Agent A tool-call events |
| `tool-calls.B` | Input | Agent B tool-call events |
| `scores` | Input | Anomaly score events |
| `drift` | Output | Detected distribution changes |

These topics are defined in the shared Kafka configuration at `infra/kafka/topics.txt`.

## 4. Input event formats

### Tool-call events

S06 accepts `tool_call.completed` and `tool_call.failed` events from the tool-call topics.

The event data should contain:

```json
{
  "event_type": "tool_call.completed",
  "event_id": "example-event-1",
  "data": {
    "agent_id": "agent-A",
    "arguments": {
      "query": "example"
    },
    "success": true
  }
}
```

The adapter extracts:

- `argument_length`: length of the compact JSON serialization of `arguments`.
- `failure_rate`: 0.0 for success and 1.0 for failure.

If `agent_id` is absent, the adapter attempts to obtain it from the topic name.

### Anomaly score events

S06 accepts `anomaly.scored` events from the `scores` topic.

```json
{
  "event_type": "anomaly.scored",
  "event_id": "example-score-1",
  "data": {
    "agent_id": "agent-A",
    "score": 0.15
  }
}
```

The adapter extracts `score` as the `anomaly_score` feature.

## 5. Detection algorithm

The implementation uses:

- Sliding window size: 100 observations.
- Statistical sample size: 30 observations.
- Significance level (alpha): 0.005.
- Random state: 42 by default.

When the window is full:

1. The detector selects 30 observations randomly from the older part of the window.
2. It takes the 30 most recent observations.
3. It compares both samples using the two-sample Kolmogorov-Smirnov test.
4. It reports drift when both conditions hold:

   - p-value <= alpha
   - KS statistic > 0.1

5. After detecting drift, it retains the most recent 30 observations as the starting window for subsequent monitoring.

Each agent-feature pair is monitored independently.

## 6. Output event

When drift is detected, S06 publishes a `drift.detected` event to the `drift` Kafka topic.

Example:

```json
{
  "schema_version": "1.0",
  "event_id": "generated-uuid",
  "event_type": "drift.detected",
  "occurred_at": "2026-11-22T21:30:42.047134+00:00",
  "run_id": null,
  "session_id": null,
  "sequence": null,
  "request_id": null,
  "data": {
    "agent_id": "agent-A",
    "detector": "kswin",
    "monitored": "anomaly_score",
    "statistic": 0.4667,
    "p_value": 0.00253,
    "alpha": 0.005,
    "window_size": 100
  }
}
```

The `monitored` field identifies which feature experienced drift.

## 7. Configuration

The following environment variables are supported:

| Variable | Default | Description |
|---|---|---|
| `KAFKA_BOOTSTRAP` | `localhost:29092` | Kafka bootstrap address |
| `KAFKA_GROUP_ID` | `s06-kswin` | Kafka consumer group |
| `KAFKA_TOPICS` | `tool-calls.A,tool-calls.B,scores` | Input topics |
| `KSWIN_WINDOW_SIZE` | `100` | Sliding window size |
| `KSWIN_STAT_SIZE` | `30` | Statistical sample size |
| `KSWIN_ALPHA` | `0.005` | Significance threshold |
| `LOG_LEVEL` | `INFO` | Logging level |

The Docker Compose configuration supplies the internal Kafka address `kafka:9092`.

## 8. Running with Docker Compose

Run these commands from the repository root:

Start Kafka:

```bash
docker compose up -d kafka
```

Initialize Kafka topics:

```bash
docker compose up kafka-init
```

Build and start S06:

```bash
docker compose up -d --build kswin
```

Check the service:

```bash
docker compose ps
docker compose logs --tail=60 kswin
```

The service should log its Kafka subscriptions.

## 10. Current limitations

- Detector windows are held in memory. Restarting the service resets its detection history.
- The `failure_rate` feature currently represents individual binary failure observations, not a separately calculated rolling failure percentage.
- The detector monitors numeric distribution changes; it does not determine whether a change represents an attack or benign concept drift.
- The implementation uses SciPy's two-sample KS test with the KSWIN sampling and decision procedure.

S08 and downstream components can use the published drift events for further analysis and decision-making.
